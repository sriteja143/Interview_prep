| #      | Topic                                                 | `ArrayList`                                                                                                                                                                                                                                                | `LinkedList`                                                                                                                                                                                         |
| ------ | ----------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **1**  | **What is it and what problem does it solve?**        | A resizable array implementation of `List`. Solves the problem of storing an ordered collection with **fast index-based access** and dynamic resizing.                                                                                                     | A doubly-linked implementation of `List` and `Deque`. Solves the problem of storing elements where **insertion/removal at known positions or both ends** can be efficient.                           |
| **2**  | **What interface/class does it implement or extend?** | Extends `AbstractList` and implements `List`, `RandomAccess`, `Cloneable`, `Serializable`.                                                                                                                                                                 | Extends `AbstractSequentialList` and implements `List`, `Deque`, `Cloneable`, `Serializable`.                                                                                                        |
| **3**  | **How does it work internally?**                      | Maintains an internal array (`Object[]`) to store references to elements. When capacity is insufficient, it allocates a larger array and copies the existing references.                                                                                   | Maintains a chain of nodes. Each node contains the element plus references to the previous and next nodes.                                                                                           |
| **4**  | **What data structure does it use internally?**       | **Dynamic/resizable array**.                                                                                                                                                                                                                               | **Doubly linked list**. Conceptually: `prev ← Node → next`.                                                                                                                                          |
| **5**  | **Important methods**                                 | `add()`, `add(index, element)`, `get()`, `set()`, `remove()`, `contains()`, `indexOf()`, `clear()`, `addAll()`, `removeIf()`, `sort()`, `subList()`.                                                                                                       | All common `List` methods plus `Deque` methods such as `addFirst()`, `addLast()`, `getFirst()`, `getLast()`, `removeFirst()`, `removeLast()`, `offer()`, `poll()`, `peek()`.                         |
| **6**  | **How are elements stored and retrieved?**            | Elements are stored in **contiguous array slots**. `get(index)` directly accesses `elementData[index]`.                                                                                                                                                    | Elements are stored in separate `Node` objects. To get an index, it traverses from the head or tail depending on which is closer.                                                                    |
| **7**  | **What happens during insertion/deletion/search?**    | At the end, insertion is usually O(1) amortized. Inserting/removing in the middle requires shifting array elements → O(n). Search requires traversal → O(n).                                                                                               | Inserting/removing a node is O(1) **once the node/position is known**. Finding the position by index/search is O(n).                                                                                 |
| **8**  | **Time and space complexity**                         | `get(index)` → O(1); `set()` → O(1); append → O(1) amortized; insert/remove middle → O(n); search → O(n). Space → O(n), with array capacity overhead.                                                                                                      | `get(index)` → O(n); `set(index)` → O(n); add/remove at ends → O(1); insert/remove at a known node → O(1); search → O(n). Space → O(n), but each element has node overhead.                          |
| **9**  | **Duplicates and `null`?**                            | Yes. Allows duplicates and multiple `null` values.                                                                                                                                                                                                         | Yes. Allows duplicates and multiple `null` values.                                                                                                                                                   |
| **10** | **Insertion/sorted order?**                           | Maintains **insertion order**. Does not automatically maintain sorted order.                                                                                                                                                                               | Maintains **insertion order**. Does not automatically maintain sorted order.                                                                                                                         |
| **11** | **Thread-safe?**                                      | No. External synchronization or concurrent collections are required when multiple threads modify it concurrently.                                                                                                                                          | No. Same situation.                                                                                                                                                                                  |
| **12** | **Limitations/common mistakes**                       | Frequent middle insertions/removals can be expensive due to shifting. Assuming capacity equals size is a mistake. Calling `remove(1)` on `List<Integer>` removes by **index**, not value.                                                                  | Poor random access, more memory per element, worse cache locality, and traversal overhead. A common mistake is assuming insertion is always O(1)—finding the insertion position can still be O(n).   |
| **13** | **When use it vs alternatives?**                      | Default choice when you need a general-purpose `List`, especially when reads/index access dominate.                                                                                                                                                        | Use when you genuinely need deque-like operations or frequent modifications at the ends/known nodes. Often `ArrayDeque` is preferable for queue/deque use cases.                                     |
| **14** | **Java 8–21 changes/behavior**                        | Added/benefited from Java 8 collection APIs such as `removeIf`, `replaceAll`, `sort`, streams, etc. Modern JDK implementations retain the dynamic-array design; newer JDKs include implementation refinements but not a fundamental data-structure change. | Java 8 added the same modern collection/default-method APIs. Its fundamental doubly-linked-node implementation remains the same.                                                                     |
| **15** | **Production/interview scenario**                     | Example: storing API results, DTOs, database query results, configuration items, or any collection where `get(i)` and iteration are common.                                                                                                                | Example: explicit deque/list behavior where operations at both ends are important. For a high-throughput queue, you'd normally investigate `ArrayDeque` or concurrent queue implementations instead. |
